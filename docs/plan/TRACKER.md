Possible in production with two editors saving at once, or the 30-second poll overlapping a save. **Fixed 2026-11-10**, [#100](https://github.com/gergodrazsdik/weesite/pull/100): `ContentLoader` runs one load at a time, so the later load always finishes later; a test holds one load mid-read and checks the newer content wins (it fails without the fix).
- F-0043 Retrying page loads (F-0037) wasn't enough: on stack #105 four browser tests failed within seconds because Chromium dropped scripts and other files mid-load, or a load hung, while another test project started Azurite containers (each start changes the runner's network). **Fixed 2026-11-10**, [#100](https://github.com/gergodrazsdik/weesite/pull/100): CI and `just test` run the browser tests first, on their own, then the other projects together (`Weesite.Tests.slnf`); about a minute longer, and the network stays still while Chromium loads.
- F-0044 A settings save in `The_banner_is_the_drawing_none_or_a_stored_image(uploaded)` failed once on CI with a plain-text 400 (an antiforgery rejection). Every test app in the Web.Tests process kept its Data Protection keys in the same folder of the user profile; on a fresh runner that folder is empty, and dozens of apps starting in parallel raced to create its first keys (a local run with an empty profile left 4 keys where one app makes 1). **Fixed 2026-11-10**, [#100](https://github.com/gergodrazsdik/weesite/pull/100): the test apps keep their keys in memory, each its own. Production is unaffected: its keys are in Blob Storage (F-0031).
- F-0045 Dropping a file on the editor's text did nothing since #84: `ws-md-editor` looked for the media picker while setting up, but `ws-media-picker.js` loads after it, so the picker wasn't ready and the drop handlers were never attached. No test covered the drop. **Fixed 2026-11-10**, [#106](https://github.com/gergodrazsdik/weesite/pull/106): the picker is looked up when a file is dropped or pasted; a browser test now drops and pastes a file.
- F-0046 A settings save failed again on CI (#107) with a plain-text 400, after F-0044's fix: the save went through, then the response came back 400 instead of the redirect. The admin form pages saved and redirected from `OnInitializedAsync`; on a POST, Blazor then looks up the posted form by name, and if the page navigated before the form had rendered, that lookup fails and its 400 replaces the redirect (reproduced by navigating before the first render). F-0044's diagnosis was probably wrong, though in-memory keys stay. **Fixed 2026-11-10**, [#110](https://github.com/gergodrazsdik/weesite/pull/110): the six form pages (editor, settings, menu, tags, theme, profile) save in the `EditForm`'s `OnSubmit`, which runs after the form has rendered and keeps the redirect.
- F-0047 The Azure SDK logged every storage request at Information, about 15 lines each: on test the web app wrote some 240,000 log lines a day, mostly the 30-second version check and Blob reads, all ingested by Log Analytics; the re-index job wrote 2,400 for one run. **Fixed 2026-11-10**, [#115](https://github.com/gergodrazsdik/weesite/pull/115): `Azure` logs at Warning, `Azure.Core` at Error (its expected 404 and 409 answers are warnings; real failures throw and are logged by the app).
- F-0048 `infra-apply` skipped #120's infrastructure change: `just merge-stack` pushes one commit per PR, GitHub keeps only the newest waiting run of a concurrency group and cancels the others, and the run for the top commit compared only with the push before it (`github.event.before`), which changed no infrastructure. The maintainer applied by hand (`workflow_dispatch`). **Fixed 2026-11-10**, [#123](https://github.com/gergodrazsdik/weesite/pull/123): a push compares with the commit of the last successful `infra-apply` run (`scripts/last-applied.sh`), so cancelled runs and failed applies are covered by the next one. Merging a stack in one push isn't possible: GitHub refuses to change the base of a stacked PR ("the pull request is part of a stack") and retargets one only after the PR below has merged, so `just merge-stack` keeps one push per PR; the cancelled runs are noise, and the base fix keeps `infra-apply` correct.
- F-0049 On Site settings, the Search index section's divider touched the Save button: `.section { margin: 0 }` comes later in `admin.css` than `.search-index`'s top margin, with the same specificity, so it won (the danger zone had the same problem, fixed in #135). **Fixed 2026-11-10**, [#140](https://github.com/gergodrazsdik/weesite/pull/140): `.section.search-index`; a browser test checks the gap below Save.
- F-0050 The editor offered a saved post's text on the next new post ("Unsaved changes from … Restore"): a new item's unsaved text is kept in the browser under "new post" or "new page", and the first save cleared only the saved item's own key; a new item has no version to compare, so nothing filtered it out. The time was also in the browser's format, not the editor's `yyyy-MM-dd HH:mm UTC`. **Fixed 2026-11-10**, [#140](https://github.com/gergodrazsdik/weesite/pull/140): the first save's redirect says `created=1`, and the editor clears the kind's "new" text; browser tests for both.
- F-0051 The footer's "built with Weesite" link opened in the same tab, taking the reader off the site. **Fixed 2026-11-10**, branch `fix/public-ui`: it opens in a new tab (`rel="noopener"`), and its accessible name says so.
- F-0052 The media picker dialog showed two scrollbars, the dialog's and its body's: the form was capped at the window's height less 2rem, the dialog at the same less its border, so both overflowed. **Fixed 2026-11-10**, branch `fix/admin-layout`: the open dialog is a flex column the form fills, and only the body scrolls.
- F-0053 Site settings showed the home page's page selector even when the home page shows only the latest posts, where it does nothing. **Fixed 2026-11-10**, branch `fix/admin-layout`: CSS `:has()` hides it while "The latest posts" is chosen (no script needed).
- F-0054 The editor listed only the current version of every post and page after #152: to hide a deleted file's versions from a new file at the same path, it kept the versions with the current one's creation time, but in Azure each version has its own creation time, so only the current one matched (Azurite has no versioning, so tests couldn't see it; the maintainer found it on test). **Fixed 2026-11-10**, branch `fix/version-history`: a new file gets a `life` ID in its blob metadata that every save carries on, and the list keeps the versions with the current one's ID; files from before have none on any version and list everything again.
- F-0055 Saving site settings on prod always said someone else had saved them. Prod starts without `site.json`; the page's hidden ETag field is then empty and comes back as an empty string, which the settings editor didn't take as "no file yet", so every save of Site settings, Menu, Tags or Colour theme was refused. Test has the sample `site.json`, and the tests had one too, so neither showed it. **Fixed 2026-11-10**, branch `fix/settings-first-save`: an empty ETag means no file; a test saves on a site without `site.json`, and Blob-mode tests cover quoted ETags and a save on Azurite.
- F-0033 Test took about 100 s to start (startup probe failures in the log stream): with `Seed:Path` the seeder processed every seed photo into WebP variants again at each start, on a quarter of a vCPU. Media names carry the file's hash, so the seeder now skips images already stored (each image's original goes up after its variants, so an interrupted start leaves nothing that looks done). Moving the content load and index build after the server starts, with a readiness probe, stays with T-0054.
- F-0032 Every public page went out with `Cache-Control: no-store` (and a log warning per request): the theme switch in the header carried an antiforgery token, and ASP.NET Core marks any response with one as uncacheable. The switch no longer uses antiforgery: a forged post can only change a colour preference. Forms that change data (`/admin`) keep it.
- F-0031 Data Protection keys (which encrypt the sign-in cookie and the antiforgery tokens) were created per container and lost on every restart; with two replicas a cookie from one couldn't be read by the other ("key was not found in the key ring" in the log stream). The keys now live in Blob Storage (`dataprotection` container, `keys.xml`), shared and kept across revisions; wrapping them with a Key Vault key follows (T-0078).
- F-0030 Right after an apply created or rotated the Microsoft client secret, the first sign-in on test failed with a 400 from Microsoft and the next one, a minute later, worked: a new secret takes a minute or so to work everywhere in Entra ID. It can recur briefly after each 180-day rotation; no change.
- F-0029 After #51, `infra-apply` failed on test with 403 "Insufficient privileges" when adding the Entra app's password (and later updating its logo). The app's owner was the plan identity: `owners` came from `azuread_client_config` (whoever runs OpenTofu), which the plan identity resolves when it computes the plan the apply carries out. With `Application.ReadWrite.OwnedBy` the apply identity could create the app but not change it. The owner is now the apply identity's service principal, looked up by name (`id-weesite-apply-<env>`). The existing test app needed the apply identity added as owner by hand once (`az ad app owner add`); the next apply removed the plan identity.
- F-0028 With real code samples, axe flagged code blocks: a block whose long lines scroll sideways is a scrollable region keyboard users can't reach (WCAG 2.1.1). Code blocks now render with `tabindex="0"`, so they take focus (with the visible focus outline) and scroll with the arrow keys.
- F-0027 Each `CodeHighlighter` loaded its own TextMate grammars (about half a second of CPU for the sample's languages). The web tests start about a hundred apps, so with 22 posts the suite went from 9 s to 55 s and the MCP client's connection timed out. Grammars now load once per process and are shared; the suite takes 6 s.
- F-0026 The container image's `ADD` from a URL writes the file as root with mode 600, so the non-root app user couldn't read the model and startup failed (`system error number 13`); the Containerfile adds `--chmod=444`, and a model that fails to load now leaves search on keywords instead of stopping the app.
- F-0025 CI flakes on #42's first run: a 100 ms `matchTimeoutMilliseconds` fired on the theme colour regex with a 20-character input, because the busy runner paused the thread (the timeout is wall-clock). Every pattern in the app is anchored and bounded, so the timeouts guarded nothing; they're now `RegexOptions.NonBacktracking` (linear time, no timeout). The same run had one Playwright `net::ERR_NETWORK_CHANGED` from the runner's network, not the app; re-run if it recurs, and add a retry to navigation only if it becomes frequent.
- F-0024 libvips draws card text through Pango and Fontconfig. The chiseled image has no Fontconfig configuration and a read-only `/tmp`: text still renders from the bundled font files, but Fontconfig prints errors. The image sets `FONTCONFIG_FILE` to the app's own `Fonts/fonts.conf` (that folder, cache in `~/.cache/fontconfig`); checked by building the image and fetching a card.
- F-0023 Once the app resources existed, plans failed for the read-only plan identity: refreshing `azurerm_container_app` calls `listSecrets`, and `azurerm_storage_table` reads the table's stored access policies (Get Table ACL), which with Entra ID needs `Microsoft.Storage/storageAccounts/tableServices/tables/getAcl/action`: no data role has it, only Contributor among built-in roles. The bootstrap gives the plan identity a custom role with exactly those actions on the environment resource groups (a first try with Storage Table Data Reader didn't help). Found on #32's plan.
